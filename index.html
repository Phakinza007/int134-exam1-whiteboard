New here? Quick glossary

Terms that repeat across the whole board — read this once before diving into W1–W5.

PID
the number the OS gives a running program, used to track and control it.
PPID
the PID of whichever process started this one (its parent).
systemd
the program that starts and looks after every other service on the machine.
unit file
a short text file telling systemd how to run one service: which command, which user, restart or not.
signal (SIGTERM/SIGKILL)
a short message asking a program to stop. SIGTERM = please stop; SIGKILL = stop now, no choice.
firewall / ufw
software that blocks network traffic by default and only lets through the ports you explicitly allow.
port
a number a program listens on, so the network knows which program a request is for (e.g. :80 for a website).
0.0.0.0 vs 127.0.0.1
0.0.0.0 = reachable from anywhere on the network. 127.0.0.1 = reachable only from this same machine (loopback).
DBMS / database server
a separate program that stores and manages data — your app is just one client, not the data itself.
least privilege
give an account only the access it truly needs, so a leak (its "blast radius") does the least possible damage.
origin
the scheme + domain + port a page was loaded from. Differ in even the port, and it's a different origin.
CORS
a browser rule blocking a page's script from reading a response from a different origin, unless that origin allows it.
reverse proxy
a server in front of other servers that forwards requests to the right one — the outside world sees only one address.
shadow database
a disposable copy of the database Prisma builds to test a schema change safely before touching the real one.
W1

Package Management & Service Manager

5 Aug 2026 A service has two independent switches: does it start at boot, and is it running right now.

Concepts

  • systemd is PID 1 — the init system that starts and supervises every other service.
  • apt is for you (interactive); apt-get/apt-cache is for scripts.
  • Ubuntu repo components: main (Canonical), universe (community), restricted, multiverse.

Commands

sudo -u user cmdrun one command as user, your own password
su useropen a shell as user, their password
apt updaterefresh metadata only — installs nothing
apt install pkg=verpin an exact version
systemctl status/start/enableruntime vs boot-time control

Watch out

  • apt update ≠ apt upgrade — updating the list installs nothing.
  • id, whoami, who am i answer three different questions, especially under sudo.
  • STEP 1/3 · W1enable ≠ start: enabled/disabled (boot) and active/inactive (now) are fully independent — see the matrix above.
W2

Managing Processes

12 Aug 2026 "It's running" is not "it's deployed" — only a unit file survives everything.

Concepts

  • A bare ps shows almost nothing — use ps aux, ps -ef, or -o fields.
  • Every process has a PID and PPID and descends from PID 1 (pstree -p).
  • A job (&) belongs to exactly one shell — invisible from any other terminal.

Commands

pgrep -af namematch the full command line, not just the name
jobs / fg %N / bg %Nlist, foreground, background a job
kill / kill -9SIGTERM (ask nicely) / SIGKILL (cannot refuse)
journalctl -u name -fSTEP 1/3 · W2follow a service's log live

Watch out

  • Of TERM/INT/HUP/KILL, only SIGKILL cannot be caught, blocked, or ignored.
  • STEP 2/3 · W2unit needs an absolute path: ExecStart= needs an absolute path — systemd runs no shell, so ~ and relative paths fail.
  • A stopped (T) process gets no CPU, so it cannot even process a kill signal — fg it first.

Deploy Static Web

19 Aug 2026 Installed does not mean started, and reachable does not mean allowed through the firewall.

Concepts

  • A URL path that names a directory falls back to index.html.
  • This course installs nginx from nginx.org (conf.d/*.conf), not Ubuntu's sites-enabled.
  • Block selection: port → server_name (exact → wildcard → regex) → default_server → first file alphabetically.

Commands

nginx -ttest config syntax before touching anything live
systemctl reload nginxsafe — keeps the old config if the new one fails
ufw allow 80/tcpSTEP 1/3 · W3open door #1 (frontend): open inbound only for what you need
curl -H "Host: x" localhosttest a server block with no DNS
journalctl -u nginxSTEP 2/3 · W3read the log when it won't start

Watch out

  • reload silently keeps serving the old config if the new one is broken — no downtime, no visible change either.
  • restart stops everything first — a broken config takes the whole site down.
  • Never touch the port 22 rule; never ufw disable.

Deploy Backend and DBMS

26 Aug 2026 Three processes, three ports, three identities — and one port that must never leave the machine.

Concepts

  • Deploy order: database, then backend — the backend depends on the database, never the reverse.
  • One application = one database = one user (least privilege / blast radius).
  • STEP 3/3 · W4same recipe, real app: same systemd recipe as week 2 — just a real app now.
  • STEP 3/3 · W4same debug order again: systemctl status, then journalctl -u the service.

Reverse Proxy and Integration

2 Sep 2026 Close the doors week 4 opened — one address in front, nginx decides where a request actually goes.
301 Client sends POST /api/notice → redirect → resent as GET — the body is silently dropped
308 Client sends POST /api/notice → redirect → resent as POST — method and body preserved

Concepts

  • A reverse proxy sits in front of origin servers — clients never talk to them directly.
  • STEP 2/2 · W5the real fix — remove the second origin: CORS is a browser rule, not a network wall — it blocks a script from reading a cross-origin response.
  • Nested-path routing lets one server_name serve both the frontend and the API.

Commands

location /api/ { proxy_pass ...; }STEP 2/2 · W5proxy stays on loopback too: forward matching paths to the backend
location / { root ...; }everything else is served as static files
return 308 https://$host$uri;redirect that preserves the HTTP method

Watch out

  • Use 308, not 301, for any redirect that might carry a POST.
  • No sample config is given in the exam — you write the server block from scratch.
  • STEP 3/3 · W5close door #2 again: once the proxy is the only caller, the backend's own port can close — only 80 needs a rule.

Every service you touched this term — nginx, MySQL, school-api — went through the same eight moves. Here they are end to end, with the reason for each.

Take this command apart
install -dmake a directory — and set its owner, group and mode in the same command
-o / -g / -mowner, group, mode. mkdir then chown then chmod is three commands and two moments where it is wrong
2775the 2 is setgid: every file created inside inherits the directory's group instead of the creator's own. That is how more than one person works on one deployment
tar -xextract. -c would create one, -t lists without unpacking
-zthe archive is gzip-compressed — the .gz half of .tar.gz
-f <file>read this file. Put it last of the letters — the filename comes straight after it
-C <dir>change into this directory first, so files land there and not wherever you are standing
--strip-components=1throw away the first path segment of every entry. The archive holds one top-level folder; without this you get /srv/noticeboard/noticeboard/backend
find -perm -u+wonly entries whose owner may write. The leading - means “at least these bits”, not “exactly”
-exec … {} +run a command on what was found. {} is the list, and + hands it over in as few runs as possible — \; would run chmod once per file

Why the find at all, when 2775 already set setgid? Look at what tar actually produced: drwxr-sr-x. The s came down from the parent so the group is right — but there is no w in it. setgid hands down the group, never the permission, and the modes inside an archive are whatever the person who built it had. And why not chmod -R g+w? Because -R grants it to everything, including files somebody deliberately made read-only. -perm -u+w writes the actual rule down: the group may write wherever the owner may, and nowhere else. Tonight the two agree; from class 6 this becomes a git repository, and git stores its objects read-only on purpose.

server {    listen      80 default_server;    server_name lvm68xxx.sit.kmutt.ac.th lvm68xxx;     access_log  /var/log/nginx/noticeboard.access.log  main;    error_log   /var/log/nginx/noticeboard.error.log   warn;     root  /var/www/noticeboard;    index index.html;     location / { try_files $uri $uri/ =404; }}
+ added  ~ value you change    already in the file
  • Don't write this from nothing. /etc/nginx/conf.d/default.conf came with the package and is a working server block — open it, read it, copy it, edit it. Adapting somebody else's configuration is most of this job, and it is what the exam asks you to do.
  • Only one block on port 80 may be default_server. The package's default.conf is in the way, and lab03 checks for it being out of service and still on the machine — so rename it rather than deleting or gutting it: sudo mv default.conf default.conf.disabled. Only *.conf is read, so the rename is the off switch. You want the default yourself because the checker probes with a hostname it invents while it runs, and being the default passes every name at once.
  • The two log lines do not take the same second argument. access_log takes a format — main, which is defined in nginx.conf; go and read it. error_log takes a level, like warn or notice: how bad a thing has to be before it gets written down. Swapping them is the usual first mistake, and nginx -t will say so.
  • Logs go directly in /var/log/nginx/ and must end in .log. Not tidiness: /etc/logrotate.d/nginx rotates /var/log/nginx/*.log, a pattern that does not look inside subdirectories and does not match any other name. A log nothing rotates grows until it fills the disk, and a full disk takes down every service on the machine, not just this one.
  • try_files $uri $uri/ =404 says: the file if it exists, then the directory index, and otherwise say plainly that there is nothing there. Without it a missing file produces something less honest.

The facts most easily turned into multiple choice

Signals — class 2

The slide gives four, and asks which one cannot be refused.

SIGHUP 1your terminal went away
SIGINT 2CTRL+C — please stop
SIGKILL 9the kernel stops it now. Cannot be caught, blocked or ignored
SIGTERM 15please shut down cleanly — this is what plain kill sends
Know the numbers. kill -l lists all sixty-four. A real service traps SIGTERM so it can finish writing to disk — correct behaviour, not a bug. So systemd asks politely, waits up to 90 seconds, then uses the one that cannot be refused.

enable is not start — classes 1 and 2

The slide repeats this title twice, and labels it “the point of the whole class”.

daemon-reloadmakes systemd re-read the unit. Required every time you edit the file
One symlink is the entire meaning of “enabled” — and it is what the [Install] stanza was for. Skip daemon-reload and systemd answers from the version it read last; it warns you, and the warning names the fix.

Straight off the slide, and exam-shaped: “I ran ps and my service wasn't there” is not evidence of anything. Without -f, pgrep matches the interpreter, not your script. And ss -tlnp only names the owning process if you are root.

Two different nginxes — class 3

This course installs from nginx.org. Most answers you find online are for the other one.

Ubuntu'sapt install nginx from the stock repo · version 1.24 · runs as www-data · sites-available + sites-enabled · site root /var/www/html
nginx.orgadd the repo yourself · version 1.30.x · runs as nginx · conf.d only, no sites-enabled · site root /usr/share/nginx/html
He called this one out as สำคัญมาก. nginx.conf includes conf.d/*.conf, so a file not ending in .conf is never read — and that is the sanctioned way to disable a config: rename it, don't delete it. Start from default.conf and copy-then-edit, so you needn't remember the syntax.

How nginx picks a server block — class 3

A ranked algorithm — the most directly examinable thing in the whole course.

1no listen at all means 0.0.0.0:80
2match IP and port first, only then look at server_name
3name order: exact, then leading wildcard, then trailing wildcard, then regex
4nothing matched? the default_server takes it
5nobody declared one? the first block read wins — and files are read in filename sort order, not the order you created them
6with only one block, server_name is never checked — everything lands there
Name conflict: the later file is ignored, and adding default_server does not fix it — the problem is the duplicate name, not the order. listen [::]:80 is IPv6. A server_name of "" matches requests with no Host header.

nginx -t, reload, restart — class 3

nginx -ttests that the config LOADS, not that it is correct. A typo'd path with valid syntax still passes
systemctl reloadre-reads the config without dropping live connections — this is the normal one
systemctl restartkills and starts again; anything in flight is dropped. For when reload is not enough
The order is: edit, nginx -t, then reload. If a reload changes nothing, suspect three things — the file isn't .conf, you edited the wrong server block, or the browser cached it.

MySQL — class 4

The half of class 4 that is pure theory: privileges and secrets.

auth_socketMySQL's root on Ubuntu doesn't check a password, it checks that you are the machine's root. Hence sudo mysql, not mysql -u root -p

Reverse proxy and CORS — class 5

The last class before the exam, and the one with the clearest “why”.

the problemfrontend on :80, backend on :3000. A different port is a different origin, so the browser blocks the call
CORSan HTTP-header mechanism by which a server names the origins a browser may load its resources from
this course's answera reverse proxy — put everything behind one origin and the CORS problem stops existing, with no headers to set
the definitiona server that transparently forwards requests to one or more web servers; it sits in front of the origin server so that no client ever talks to it directly
what it buysscalability, performance, resilience and security — those four words, straight off the slide
From the slide's diagrams: without a proxy the user has to type host:3000 to reach the API. With one, they ask /api/notices on port 80 and nginx forwards to localhost:3000. In the nested form the user asks /school/api/students and nginx strips /school before forwarding as /api/students.

Reading a status code for whose fault it is

In a timed practical this is the single biggest time-saver.

2xxit worked. Look somewhere else
301 / 308both permanent. 308 preserves the method and body; with 301 a browser may turn a POST into a GET
404nginx was reached but found no file or location — check root, check the location block
502nginx forwarded and the backend didn't answer — it's down, or listening on another port
504the backend accepted but took too long
no response at allnot a status code at all. You never reached nginx — suspect ufw, or that nginx isn't running
Rule of thumb: 4xx blames the request, 5xx blames the server, no code at all blames the network. On a 502, go straight to journalctl -u for the backend.

The firewall, ufw

ufw status numberedlists the rules with the numbers you need in order to delete one
ufw allow 80/tcpopen the web port
ufw delete Ndelete by number — and the numbers shift afterwards, so re-list every time
Never delete the rule for port 22. He said in class that if you do, you wait for an admin — he cannot fix it for you, because fixing it would need port 22. And an opened port that ss doesn't show simply means nothing is listening on it yet; that's a separate problem.
CORS — the last topic inside the line

Who actually refuses

If you remember one thing from the whole topic, this is it.

the serveranswered 200 with the data. It refused nothing, and its log shows nothing unusual
the browserfetched the answer, looked for permission to hand it to that page, found none, and threw it away
whenafter a successful response — not before the request went out
against whomonly the page that asked. Anyone else asking the same URL is unaffected
The consequence you can answer with. Seeing 200 with a full body in the Network tab while the page shows nothing is not a contradiction — it is the signature of CORS. It is also why curl cannot reproduce the failure at all.

The same URL, asked four ways

Lab 5 walks these in order, because each one rules something out.

Consolesays why the browser stopped it. Read the whole message, not the first line: it names two addresses and the header it could not find
Networksays whether the request was made at all, and what came back. It was, and 200 did
curlgets the data, because no page is asking on anyone's behalf. Debugging CORS with curl is testing the wrong thing
address bargets the data. Same browser, same URL — this time no page from elsewhere is doing the asking
When you test, ask for the same address the page asked for, not the loopback — otherwise you changed two things at once and the result proves nothing.

What makes two URLs different origins

Scheme, host and port — all three must match. Compared against a page served from http://lvm68xxx.sit.kmutt.ac.th.

…:3000different — the port. This is our case all class
https://…different — the scheme
http://lvm68xxxdifferent — the host, even though it is literally the same machine
http://127.0.0.1different — the host again
…/api/noticessame — a path is not part of an origin
That last row is the whole of the reverse proxy. Because a path is not part of an origin, moving the API under /api/ of the address you already have deletes the second origin rather than configuring around it.

The missing header, and the setting

Access-Control-
Allow-Origin		the header the browser looks for in the reply and does not find. Its name is in the Console message too
CORS_ORIGINlives in the backend's .env. Set it to the address the page is served from — scheme, host and port
string comparecompared literally. A trailing slash does not match; the host without the port does not match. A nearly-right value fails in a way that looks like broken code
restartnot reload — an environment file is read once, when the process starts
the journal linethe app says on startup: cors: allowing … or cors: disabled (CORS_ORIGIN is not set). Read it before you go on
Exactly the shape of class 4's percent-encoding lesson: a value that is very nearly right does not announce itself as wrong, it simply does not work, and it sends you looking somewhere else.

Two fixes, and why the course prefers the second

set CORS_ORIGINit works. But the API's configuration now holds the page's address: move the page's port and you must edit the API's .env and restart it too. Two things to keep in step
reverse proxyremoves the second origin. Nothing to configure, nothing to keep in step, and it lets you close the extra port as well
lab 5 asksthe API's origin rule is set — or the proxy has made it unnecessary. Either answer passes
The lab's own question at this point: suppose you had to move the page to a different port tomorrow — what else would you have to change, and where does each of those live? Nothing in the first fix is wrong; there is simply more of it than there needs to be. That is the answer the paper is after.
The ones people actually get wrong — said out loud in class
The file must end in .conf He called this one สำคัญมาก. nginx.conf includes only conf.d/*.conf. Any other name is never read, and you spend twenty minutes wondering why your edit did nothing.

Try them yourself — each one opens to its answer
A script traps TERM and you run systemctl stop. What happens?
It waits up to 90 seconds, then systemd sends SIGKILL.systemd sends SIGTERM first; the trap catches it, so nothing dies. When the timer runs out it uses signal 9, which cannot be caught. This is why “systemctl stop sometimes waits” is not a bug.
is-enabled says enabled, is-active says inactive. What does that mean?
It will come up at the next boot, but it is not running now.The symlink in multi-user.target.wants exists — that is the whole meaning of enabled — but nobody has started it. systemctl start for now, or enable --now to do both.
You put a config at /etc/nginx/conf.d/site.txt and reloaded. Nothing changed. Why?
nginx.conf includes conf.d/*.conf only, so a .txt is never read.And nginx -t passes, because a file that is never read has nothing to be wrong in. The same fact is the correct way to disable a config: rename it rather than delete it.
One server block, no default_server, and the requested name doesn't match its server_name. What happens?
The request still lands there.With a single block nginx never checks server_name; everything arriving on that IP and port goes to it. People miss this because they expect a name mismatch to be rejected.
The API returns 502 Bad Gateway. Where do you look first?
At the backend, not at nginx.502 means nginx accepted the request and forwarded it, and the far end did not answer. In order: systemctl status for the backend, journalctl -u for it, then ss -tln to see whether it is listening on the port proxy_pass names.
You ran ufw allow 8080/tcp but ss -tln doesn't show 8080. What's wrong?
Nothing. Nothing is listening on it yet.ufw opens the door; ss says whether anyone is waiting behind it. Different layers — he used this exact example in class. The right order is: start the service, confirm with ss, then open the firewall.
Why npm ci on a server rather than npm install?
ci installs exactly the lockfile; install may rewrite it.Which means production can end up with versions you never tested, and the next deploy with different ones again — the hardest class of bug to chase. ci also wipes node_modules first, so the result is identical every time.
migrate dev vs migrate deploy — and which must never run on a server?
Never migrate dev.migrate dev exists to author migrations during development, and it will reset the database when it finds a mismatch. migrate deploy applies existing migrations only — it authors nothing and destroys nothing. That is the production one.
Why does this course solve CORS with a reverse proxy instead of setting headers?
Because behind one origin the problem never arises.CORS appears because the frontend is on :80 and the backend on :3000 — a different port is a different origin. Once nginx takes everything on :80 and forwards to localhost:3000, the browser sees one origin, so there are no headers to set. The slide adds that you get scalability, performance, resilience and security along with it.
Your script is running but pgrep myapp finds nothing. Why?
You need -f. Plain pgrep matches the process name, which for a script is the interpreter.A bash script shows up as bash, not myapp.sh. -f matches the whole command line, which contains the filename. The slide says outright: you will hit this today.
Why is MySQL's root reached with sudo mysql rather than mysql -u root -p?
Because that account uses auth_socket: it checks that you are the machine's root, not a password.Trying mysql -u root -p gives ERROR 1045 (28000) Access denied — which does not mean the password is wrong, it means you authenticated the wrong way entirely.
Why utf8mb4 and not utf8?
Because MySQL's utf8 stores at most three bytes per character.Anything needing four — emoji, for instance — is lost or makes the insert fail. utf8mb4 is real UTF-8; MySQL's utf8 is a historical misnomer. So name utf8mb4 at CREATE DATABASE time, every time.
Why single-quote the password in .env and in an export?
Because a generated password can contain characters the shell interprets.An =, a * or a $ truncates the line or gets substituted behind your back, and you end up with a silently wrong password. Single quotes switch all interpretation off, and a MySQL-generated password never contains one, so it is always safe. Separately: in a connection string those characters must be percent-encoded, and encoding twice gives a wrong password with no warning at all.
A question says “it must come back by itself after a reboot”. What does it want?
A unit file plus systemctl enable — then a reboot to prove it.This is the wording he described: it names the outcome, not the command. “Survives a logout” can be nohup. “Survives a reboot” or “restarts itself when it crashes” cannot — only a unit file, and it is Restart= and WantedBy= that do it.
The page cannot reach the API, but curl on the VM reaches the same address fine. What does that tell you?
The API is fine and so is the network. What differs is who was asking.curl is not asking on behalf of any page, so there is nobody to withhold the answer from. Typing the same URL into the address bar gets the data too, which rules out the API, the network and the browser itself — leaving only that the request came from a script in a page served by another origin.
The Network tab shows 200 with the full JSON body, but the page renders nothing. Where is the problem?
In the browser, after the response arrived. Not at the server at all.The browser fetched the response, looked for Access-Control-Allow-Origin among its headers, did not find one, and refused to hand it to the script. That is not a contradiction — it is the signature of CORS, and it is why the server's log looks entirely normal.
The page is on :80 and the API on :3000, same hostname, same machine. Same origin?
No. A different port is a different origin.An origin is scheme + host + port, and all three must match; being on the same machine is irrelevant. A path, however, is not part of an origin — so /api/notices on that same port 80 is the same origin, and that is the entire reason a reverse proxy works.
You set CORS_ORIGIN, restarted, and the page is still empty. What do you check first?
The cors: line in the journal as the service came up — then whether the value matches character for character.The app prints cors: allowing … or cors: disabled (CORS_ORIGIN is not set) on startup. disabled means it never read your value — did you reload instead of restart? allowing and still failing means comparing it character by character with the address the Console printed: a stray trailing slash and a missing port are the two usual culprits, and neither announces itself.
With a reverse proxy in place, why is CORS_ORIGIN no longer needed?
Because there is no cross-origin request left to permit.CORS_ORIGIN is a way of asking permission to cross a boundary; the proxy removes the boundary. The page asks /api/notices on the very origin it was served from, so the browser has nothing to check. The knock-on benefits are that no value has to be kept in step in two places, and that port 3000 can be closed — which is what lab 5 actually tests.
