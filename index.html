New here? Quick glossary

Terms that repeat across the whole board — read this once before diving into W1–W5.

PID
the number the OS gives a running program, used to track and control it.
PPID
the PID of whichever process started this one (its parent).
systemd
the program that starts and looks after every other service on the machine.
unit file
a short text file telling systemd how to run one service: which command, which user, restart or not.
signal (SIGTERM/SIGKILL)
a short message asking a program to stop. SIGTERM = please stop; SIGKILL = stop now, no choice.
firewall / ufw
software that blocks network traffic by default and only lets through the ports you explicitly allow.
port
a number a program listens on, so the network knows which program a request is for (e.g. :80 for a website).
0.0.0.0 vs 127.0.0.1
0.0.0.0 = reachable from anywhere on the network. 127.0.0.1 = reachable only from this same machine (loopback).
DBMS / database server
a separate program that stores and manages data — your app is just one client, not the data itself.
least privilege
give an account only the access it truly needs, so a leak (its "blast radius") does the least possible damage.
origin
the scheme + domain + port a page was loaded from. Differ in even the port, and it's a different origin.
CORS
a browser rule blocking a page's script from reading a response from a different origin, unless that origin allows it.
reverse proxy
a server in front of other servers that forwards requests to the right one — the outside world sees only one address.
shadow database
a disposable copy of the database Prisma builds to test a schema change safely before touching the real one.
W1

Package Management & Service Manager

5 Aug 2026 A service has two independent switches: does it start at boot, and is it running right now.

Concepts

  • systemd is PID 1 — the init system that starts and supervises every other service.
  • apt is for you (interactive); apt-get/apt-cache is for scripts.
  • Ubuntu repo components: main (Canonical), universe (community), restricted, multiverse.

Commands

sudo -u user cmdrun one command as user, your own password
su useropen a shell as user, their password
apt updaterefresh metadata only — installs nothing
apt install pkg=verpin an exact version
systemctl status/start/enableruntime vs boot-time control

Watch out

  • apt update ≠ apt upgrade — updating the list installs nothing.
  • id, whoami, who am i answer three different questions, especially under sudo.
  • STEP 1/3 · W1enable ≠ start: enabled/disabled (boot) and active/inactive (now) are fully independent — see the matrix above.
W2

Managing Processes

12 Aug 2026 "It's running" is not "it's deployed" — only a unit file survives everything.

Concepts

  • A bare ps shows almost nothing — use ps aux, ps -ef, or -o fields.
  • Every process has a PID and PPID and descends from PID 1 (pstree -p).
  • A job (&) belongs to exactly one shell — invisible from any other terminal.

Commands

pgrep -af namematch the full command line, not just the name
jobs / fg %N / bg %Nlist, foreground, background a job
kill / kill -9SIGTERM (ask nicely) / SIGKILL (cannot refuse)
journalctl -u name -fSTEP 1/3 · W2follow a service's log live

Watch out

  • Of TERM/INT/HUP/KILL, only SIGKILL cannot be caught, blocked, or ignored.
  • STEP 2/3 · W2unit needs an absolute path: ExecStart= needs an absolute path — systemd runs no shell, so ~ and relative paths fail.
  • A stopped (T) process gets no CPU, so it cannot even process a kill signal — fg it first.
W3

Deploy Static Web

19 Aug 2026 Installed does not mean started, and reachable does not mean allowed through the firewall.

Concepts

  • A URL path that names a directory falls back to index.html.
  • This course installs nginx from nginx.org (conf.d/*.conf), not Ubuntu's sites-enabled.
  • Block selection: port → server_name (exact → wildcard → regex) → default_server → first file alphabetically.

Commands

nginx -ttest config syntax before touching anything live
systemctl reload nginxsafe — keeps the old config if the new one fails
ufw allow 80/tcpSTEP 1/3 · W3open door #1 (frontend): open inbound only for what you need
curl -H "Host: x" localhosttest a server block with no DNS
journalctl -u nginxSTEP 2/3 · W3read the log when it won't start

Watch out

  • reload silently keeps serving the old config if the new one is broken — no downtime, no visible change either.
  • restart stops everything first — a broken config takes the whole site down.
  • Never touch the port 22 rule; never ufw disable.
W4

Deploy Backend and DBMS

26 Aug 2026 Three processes, three ports, three identities — and one port that must never leave the machine.

Concepts

  • A database is a separate server with its own users — the app is only a client.
  • Deploy order: database, then backend — the backend depends on the database, never the reverse.
  • One application = one database = one user (least privilege / blast radius).
  • STEP 3/3 · W4same recipe, real app: same systemd recipe as week 2 — just a real app now.
  • STEP 3/3 · W4same debug order again: systemctl status, then journalctl -u the service.

Commands

CREATE USER ... RANDOM PASSWORDa 20-char password, shown once
GRANT ALL ON db.* TO 'x'@'localhost'scope to one database, one host
install -m 600 /dev/null x.envprivate file, before the secret goes in
npm ci && npx prisma generateexact versions, then build the client
migrate diff --exit-code0 = the database matches the code, 2 = they've drifted apart — check before starting
sudo ufw allow 3xxx/tcpSTEP 2/3 · W4open door #2 (API): one more door, this time for the API

Watch out

  • STEP 1/2 · W4never expose the database: never open port 3306 — reach MySQL over an SSH tunnel (Workbench), not the network.
  • migrate dev failing on the shadow database (see glossary) is correct — don't widen the grant (the user's permissions) to silence it.
  • Write the password literally in .env, never ${VAR} — systemd doesn't expand it.
  • STEP 1/2 · W4the setting is already there: .env already carries a CORS setting this week — it just isn't used until next week.
W5

Reverse Proxy and Integration

2 Sep 2026 Close the doors week 4 opened — one address in front, nginx decides where a request actually goes.
301 Client sends POST /api/notice → redirect → resent as GET — the body is silently dropped
308 Client sends POST /api/notice → redirect → resent as POST — method and body preserved

Concepts

  • A reverse proxy sits in front of origin servers — clients never talk to them directly.
  • STEP 2/2 · W5the real fix — remove the second origin: CORS is a browser rule, not a network wall — it blocks a script from reading a cross-origin response.
  • Nested-path routing lets one server_name serve both the frontend and the API.

Commands

location /api/ { proxy_pass ...; }STEP 2/2 · W5proxy stays on loopback too: forward matching paths to the backend
location / { root ...; }everything else is served as static files
return 308 https://$host$uri;redirect that preserves the HTTP method

Watch out

  • Use 308, not 301, for any redirect that might carry a POST.
  • No sample config is given in the exam — you write the server block from scratch.
  • STEP 3/3 · W5close door #2 again: once the proxy is the only caller, the backend's own port can close — only 80 needs a rule.

W1–5

One Recipe, Five Times — and why each step matters

Every service you touched this term — nginx, MySQL, school-api — went through the same eight moves. Here they are end to end, with the reason for each.
1sudo apt install nginx -y The software has to exist on disk before anything else can happen. Always check the version — packagers decide differently (nginx stays stopped after install; MySQL starts itself).
2micro .env A fresh install or copy only ships generic defaults. Your student ID, your port, your connection string exist only because you typed them in.
3nginx -t A reload keeps serving the OLD config if the new one is broken — nothing looks different from the outside. Test first, or you won't even notice it failed.
4sudo systemctl daemon-reload && sudo systemctl enable --now <svc> daemon-reload tells systemd to re-read the unit file you just edited. enable (boot) and active (now) are separate switches — a reboot only revives what's enabled.
5sudo ufw allow 80/tcp Default is deny-all. Every port you open is a promise to keep watching it — never the database's own port (3306).
6systemctl status <svc> → ss -tln → curl localhost → curl <public address> Checking in this order tells you which layer is actually broken instead of guessing: is it running, is it listening, does localhost see it, does the outside world see it.
7location /api/ { proxy_pass http://127.0.0.1:3xxx/; proxy_set_header Host $host; } One address for the outside world, no CORS problem — and the port you opened just to test in step 5 can close again.
8int134 check labNN "It's running right now" is not "it's deployed." Only checking proves it survives a reboot, a crash, and you walking away.
0 → 1

Hand-held: from an empty VM to a working site

Every command and every path, in the order you actually type them. At the end you have a noticeboard you can open from your own laptop — and it survives a reboot.

Phase 1 · Get in, get nginx running

Why this phase: Nothing on this machine is reachable from outside until something is listening on a port and the firewall lets it through — nginx is that front door, and everything later either serves through it or hides behind it. Doing it first also means DNS, SSH or firewall trouble surfaces now, while there is nothing else to blame it on.
By the end: http://lvm68xxx.sit.kmutt.ac.th/ shows the "Welcome to nginx" page.
1
ssh sysadmin@lvm68xxx.sit.kmutt.ac.th
Password comes from your @ad.sit.kmutt.ac.th email. You land in /home/sysadmin — confirm with pwd.
2
curl -fsSL https://nginx.org/keys/nginx_signing.key \ | sudo gpg --dearmor -o /usr/share/keyrings/nginx-archive-keyring.gpg
The key lands at /usr/share/keyrings/nginx-archive-keyring.gpg — it's what proves the packages really came from nginx.org.
3
echo "deb [signed-by=/usr/share/keyrings/nginx-archive-keyring.gpg] http://nginx.org/packages/ubuntu $(lsb_release -cs) nginx" \ | sudo tee /etc/apt/sources.list.d/nginx.list
The repo file is /etc/apt/sources.list.d/nginx.list and must stay one single line — if pasting breaks it in two, apt reports a malformed entry.
4
sudo apt update && sudo apt install nginx -y nginx -v
You must see 1.30.x. If you got 1.24, the repo didn't take — redo steps 2–3 and install again.
5
sudo systemctl enable --now nginx systemctl is-enabled nginx ; systemctl is-active nginx
Installing nginx does not start it — you have to. Those last two commands must answer enabled and active.
6
sudo ufw allow 80/tcp curl -s http://localhost/ | head -3
The curl goes over loopback and ignores the firewall entirely; the port-80 rule is what lets your own laptop reach it.

Phase 2 · Put the frontend on it

Why this phase: A web server with no content proves the server works and nothing about your deployment. This is where the machine starts serving your files under your name — and where you set the split everything later depends on: source in /srv, published copy in /var/www. Get it wrong here and every later phase inherits it.
By the end: your VM's own name shows the noticeboard page. The "add notice" button still won't work — that's expected.
7
sudo install -d -o sysadmin -g sysadmin -m 2775 /srv/noticeboard tar -xzf /home/public/labs/lab03/noticeboard.tar.gz -C /srv/noticeboard --strip-components=1 find /srv/noticeboard -perm -u+w -exec chmod g+w {} +
Source lives at /srv/noticeboard. No sudo on tar — it would overwrite the permissions you just set. Don't skip the find line: setgid (the 2 in 2775) hands down the group but never the write bit, and lab03's checker tests for it.
8
sudo install -d -o sysadmin -g sysadmin -m 2775 /var/www/noticeboard sudo rsync -a --chmod=D755,F644 --delete --exclude config.js \ /srv/noticeboard/frontend/ /var/www/noticeboard/
nginx serves /var/www/noticeboard only. Never point it at /srv/noticeboard — that folder also holds the backend, the README, and later a .git directory.
9
cp /srv/noticeboard/frontend/config.example.js /var/www/noticeboard/config.js micro /var/www/noticeboard/config.js
Put your own 11-digit student ID into /var/www/noticeboard/config.js — the checker reads it. Leave noticesUrl alone for now.
10
sudo micro /etc/nginx/conf.d/noticeboard.conf
The server block goes in /etc/nginx/conf.d/noticeboard.conf and needs: listen 80 default_server; · a server_name claiming both of your VM's names · root /var/www/noticeboard; · index index.html; · and its own /var/log/nginx/noticeboard.access.log and …error.log.
11
sudo nginx -t && sudo systemctl reload nginx curl -s http://127.0.0.1/config.js
Always test before reloading. If nginx -t fails, the reload does nothing and the old config keeps serving — it looks fine while your change quietly isn't live.

Phase 3 · The database

Why this phase: The backend cannot start without a database to connect to — bring it up second and the API just crashes, restarts, crashes again, burning CPU for nothing. This is also where the app loses the ability to damage anything beyond its own data: one app, one database, one user. Cheap to decide now, painful to retrofit.
By the end: your own database and user exist, and the password lives in exactly one file.
12
sudo apt install mysql-server -y systemctl is-enabled mysql ; systemctl is-active mysql
Unlike nginx, MySQL enables and starts itself on install. You don't run enable --now here.
13
sudo mysql
You get in with no password because the admin account is tied to your OS user (auth_socket). Try plain mysql -e "SELECT 1;" and you'll get ERROR 1045 — that's correct behaviour.
14
CREATE DATABASE noticeboard CHARACTER SET utf8mb4; CREATE USER 'noticeboard'@'localhost' IDENTIFIED BY RANDOM PASSWORD; GRANT ALL PRIVILEGES ON noticeboard.* TO 'noticeboard'@'localhost'; exit
Copy the 20-character password it prints, right now. The server keeps only a hash and cannot tell you again — if you lose it, generate a new one with ALTER USER … IDENTIFIED BY RANDOM PASSWORD;.
15
MYSQL_PWD='<the 20 characters>' mysql -u noticeboard noticeboard -e "SHOW GRANTS;"
Prove the credential works before you paste it anywhere. The MYSQL_PWD= prefix keeps it out of ps and your history — never stick it to -p. ⚠️ Unlike school, noticeboard ships no db/ folder: this password's only home is /srv/noticeboard/backend/.env in step 18, and it must differ from your school one — lab04's checker compares them.

Phase 4 · The backend

Why this phase: This is the first thing on the machine that accepts something rather than just handing files out, and the first that has to keep working without you sitting there. So everything here is about handing it to systemd properly — turning "it runs" into "it comes back": after a crash, after a logout, after a reboot.
By the end: the API answers on port 3000 as a service that survives a reboot.
16
curl -fsSL https://deb.nodesource.com/gpgkey/nodesource-repo.gpg.key \ | sudo gpg --dearmor -o /usr/share/keyrings/nodesource.gpg echo "deb [signed-by=/usr/share/keyrings/nodesource.gpg] https://deb.nodesource.com/node_24.x nodistro main" \ | sudo tee /etc/apt/sources.list.d/nodesource.list sudo apt update && sudo apt install nodejs -y node -v
Exactly the same shape as nginx: key → repo file → update → install. You need Node 24; Ubuntu's own package is the dead v18.
17
cd /srv/noticeboard/backend npm ci
Use npm ci, not npm install — ci installs exactly what package-lock.json records instead of quietly picking newer versions.
18
install -m 600 .env.example .env micro /srv/noticeboard/backend/.env
The app's settings live at /srv/noticeboard/backend/.env: DATABASE_URL with the percent-encoded password, plus STUDENT_ID, PORT=3000, HOST=0.0.0.0. Write the password literally — ${VAR} is not expanded by systemd.
19
npx prisma migrate deploy npx prisma generate
migrate deploy is the operator's command — it applies the migration that already ships. migrate dev is the developer's and will fail on the shadow database; that's correct, don't fix it by widening the grant.
20
sudo micro /etc/systemd/system/noticeboard-api.service
Unit file at /etc/systemd/system/noticeboard-api.service with User=sysadmin · WorkingDirectory=/srv/noticeboard/backend · EnvironmentFile=/srv/noticeboard/backend/.env · ExecStart=/usr/bin/node server.js (the interpreter needs its absolute path) · Restart=always · After=network-online.target mysql.service · WantedBy=multi-user.target.
21
sudo systemctl daemon-reload sudo systemctl enable --now noticeboard-api sudo ufw allow 3000/tcp curl -s http://127.0.0.1:3000/api/health
If it won't start, read journalctl -u noticeboard-api -n 20 first — it's almost always the .env or a non-absolute ExecStart. Port 3000 is open only temporarily; phase 5 closes it again.

Phase 5 · Join them up, then shut the extra door

Why this phase: The page and the API currently live at two addresses, which the browser treats as two origins and blocks. You can paper over that with CORS headers — or remove the second origin by putting nginx in front. The second way also lets you close the port you only ever opened to test, which is the whole point: a finished system exposes exactly one door.
By the end: everything arrives on port 80 alone, no CORS, and port 3000 is closed again.
22
sudo micro /etc/nginx/conf.d/noticeboard.conf
Add to the same file: location /api/ { proxy_pass http://127.0.0.1:3000/; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; } — without the headers the backend only ever sees Host: 127.0.0.1.
23
micro /var/www/noticeboard/config.js sudo nginx -t && sudo systemctl reload nginx
Change noticesUrl to just /api/notices — a bare path, no host and no port. Same origin now, so the CORS problem disappears instead of being configured around.
24
sudo micro /srv/noticeboard/backend/.env sudo systemctl restart noticeboard-api sudo ufw delete allow 3000/tcp
Set HOST to 127.0.0.1 so the API only listens locally — nginx reaches it over loopback anyway. Use restart, not reload: EnvironmentFile is read only at start. Then close the port you opened in step 21. ⚠️ This is the week-5 end state. If you're submitting lab04, stop at step 21 — that checker wants HOST=0.0.0.0 and probes the API from outside.

Phase 6 · Prove it's actually deployed

Why this phase: Everything up to here proves the system works while you are standing next to it. Deployment is the claim that it keeps working when you are not — so the only honest test is to take the machine away from yourself and watch it come back. Skipping this is exactly how people find out on exam day that a service was never enabled.
Do not skip this. "It's running right now" is not the same claim as "it's deployed".
25
systemctl is-enabled nginx mysql noticeboard-api systemctl is-active nginx mysql noticeboard-api sudo ufw status
All six answers must come back enabled/active, and ufw should list only 22 and 80. Seeing 3000 or 3306 there means you left a door open.
26
curl -s http://127.0.0.1/api/notices curl -s -X POST -H 'Content-Type: application/json' \ -d '{"author":"68xxxxxxxxx","message":"hello"}' http://127.0.0.1/api/notices
Go through nginx's /api/, not port 3000 directly — that's what proves the proxy works. And only a POST through the API counts as proof the app can write.
27
sudo reboot
Wait a minute, ssh back in, and run steps 25 and 26 again. Anything that comes back inactive was never really enabled — that gap is the whole difference between running and deployed.
